## 実DB検証チェックリスト（⏸人間待ち：接続鍵を持つ担当者が cloud.html で実施）

`cloud.html` で以下を上から順に確認する。エージェントは接続鍵を作成・コミットしない
ため、この検証は人間ゲート。**すべて緑になるまで dev→main のマージ（＝公開）はしない。**

- [ ] Supabaseプロジェクトを作成（東京リージョン推奨）
- [ ] SQL Editor で `supabase/schema.sql` → `supabase/schema_v2_rpc.sql` → `supabase/schema_v2_1_fix_rls.sql` の順に実行
- [ ] Authentication で Email ログインを有効化（確認メールの要否はプロジェクト方針に合わせる）
- [ ] 運営アカウントを作成し、その UUID を `admins` テーブルに登録（`schema_v2_rpc.sql` 末尾の手順）
- [ ] （任意）`supabase/seed_pilot.sql` を実行し、島の実在病院3院＋サンプル募集を投入
- [ ] `js/config.example.js` を `js/config.js` にコピーし、`SUPABASE_URL`・`SUPABASE_ANON_KEY` を記入。パイロット時は `DEMO_MODE: false` を推奨
- [ ] `cloud.html` をブラウザで開き、「⏸未接続」画面が**出ない**こと（config.js が読めている）を確認

### 1. 未接続ガード（回帰確認）

- [ ] デモ版 `index.html` は接続鍵の有無に関係なく従来通り動くこと（cloud切替がデモ版に影響しない）

### 2. 医師アカウント（アカウントA）

- [ ] 新規登録（医師）→ ログイン → セッションがリロード後も復元される（`get_my_profile` 経由）
- [ ] 実在確認前は「実在確認待ち」状態で、募集への手上げが資格ゲートで止まること（＝失敗が正解）
- [ ] 地図タブ・日付タブに募集が表示され、絞り込み（業務種別×エリア）が効くこと

### 3. 運営アカウント（admin）

- [ ] ログイン → 実在確認待ちキューにアカウントAの医師が表示される
- [ ] 医師の「実在確認」を承認 → AuditLog に記録が残る
- [ ] 運営画面にチャット・マッチングへ介在する導線が**無い**こと（Legal by Design 維持の目視確認）

### 4. 病院アカウント（アカウントB）＋ 全ループ

- [ ] 新規登録（病院）または `seed_pilot.sql` の病院＋招待コードで参加 → 実在確認（運営）
- [ ] 募集を公開（募集ウィザード：日付・時間帯・業務種別・診療科・報酬。報酬未入力バリデーションが効くこと）

### 5. ダブルブッキング防止（実DBでの再確認）

- [ ] 同一医師が同日時の別募集に重複応募 → DB層（`pg_advisory_xact_lock` 付き RPC）で拒否されること
